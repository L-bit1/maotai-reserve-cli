# V+1 / V+2 运维升级说明

在**同样 IP 条件**下，提升体验、成功率与运维效率（相对 Hygge / campus / ken 等开源方案）。

---

## V+1：运营闭环

| 能力 | 说明 | 入口 |
|------|------|------|
| **门店 `@` 优先级链** | `shop_id: "店A@店B@店C"`，失败自动换下一家 | 账号编辑 / credentials |
| **出口 429 健康看板** | 每组 egress 红/黄/绿、24h 429 次数、冷却秒数 | Web **仪表盘** |
| **手机 Worker 分片** | `worker_shard: phone-01`，多台手机各管 ≤20 号 | 设置 → **自动分配手机分片** |
| **待登录按分片** | App 拉 `pending-login?worker_shard=phone-01` | 管理 App |
| **预约结果写健康度** | 手机/服务器预约失败含 429 自动记入出口组 | 自动 |

### 门店链示例

```yaml
# Web 账号 shop_id 或 credentials.json
"shop_id": "100330100004@133330100001@100330100002"
```

## V+2：混合执行 + 代理信誉

| 能力 | 说明 |
|------|------|
| **混合路由** | `reserve_execution.mode=hybrid`：有代理 → 服务器；无代理 → 手机 |
| **429 动态降载** | 出口组冷却期内 **自动跳过** 服务器定时预约 |
| **代理信誉池** | 06:30 定时 + 手动「探测代理信誉」；结果写入 egress_health |
| **规模建议** | 仪表盘显示建议代理组数 / 手机台数（按启用账号数） |

### 推荐配置

```yaml
reserve_execution:
  mode: hybrid   # 或 mobile（纯手机）

antidetect:
  reserve_429_cooldown: 90   # 出口冷却秒数
```

### API

| 方法 | 路径 |
|------|------|
| GET | `/api/v1/optimization/egress-health` |
| GET | `/api/v1/optimization/execution-plan` |
| POST | `/api/v1/optimization/probe-proxies` |
| POST | `/api/v1/optimization/assign-worker-shards` |
| GET | `/api/v1/mobile/worker-bundle?worker_shard=phone-01` |
| POST | `/api/v1/accounts/batch-worker-shard` |

## 业务员 SOP（1000 号）

1. **设置** → 自动分配手机分片（每 20 号 → `phone-01`…）
2. 每台手机 App 登录后，在设置里填 **worker_shard**（与分片名一致）
3. 待登录 / 本机预约仅拉本机分片账号
4. 仪表盘每日看 **出口健康**；红色组暂停该组 Web 发码，改 4G 本机
5. `mode=hybrid` 时：仅代理组走服务器 9 点，其余靠手机
